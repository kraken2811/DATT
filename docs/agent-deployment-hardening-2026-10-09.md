## Root causes and fixes

1. **HTTP 200/403 contract mismatch** — test_same_ip_different_session_tokens_isolation expected an empty, non-enumerating 200/not_found response when one anonymous session requested another anonymous session's handle. The registry performed a global thread lookup and returned 403 before applying this contract. GET now conceals that anonymous handle without reading its checkpoint or returning its metadata. Signed cross-user access remains 403; cross-owner writes and deletion remain 403. Authentication failures remain 401/403. No existing assertion was changed.
2. **Vehicle-query authorization bypass** — test_sensitive_operational_tool_authorization_enforcement exposed two defects: Vietnamese plate membership queries could route to search_events instead of search_watchlist, and only search_watchlist was guarded. Membership/history intent is now distinguished. All ten operational tools (Face, Vehicle, Event, Camera, statistics, Alert, Notification and Report) share the same policy; supplied user IDs never imply authentication. Direct data APIs and legacy operational/media aliases also require verified credentials when strict/operational auth or persistent production mode applies. RAG retrieval remains unchanged.
3. **Public signing-secret fallback** — auth.py previously used a publicly known hardcoded HMAC key. It is removed and explicitly rejected if configured. Production/persistent deployment requires a configured key of at least 32 characters and DATT_STRICT_AUTH=1; the managed runner validates this before starting. Explicit development/test with DATT_REQUIRE_PERSISTENCE=0 may use a random process-local key if no key is configured. This key is not stable across restarts. No secret is printed or added to Git.
4. **Persistence fail-open** — missing PostgreSQL, pool/setup failures, a cached MemorySaver or an explicit memory override could undermine a persistent-history configuration. Required persistence now rejects these cases; failed pools are closed/reset. Cached graphs revalidate their saver. The API returns a sanitized 503 on history/graph infrastructure failure, instead of a misleading success. Live PostgreSQL behavior has not been executed here.
5. **Unfiltered summaries** — alert status totals and camera rankings ignored subsets of date, camera, status and entity filters; notification status totals used all notifications. One common filtered relation now drives rows, unpaginated totals, status summaries and alert rankings. It handles face/plate event IDs, target/watchlist UUIDs, camera UUID/registry aliases, normalized plates and literal text search. Invalid dates, UUIDs, event types/statuses and reversed ranges produce unavailable/error responses, never silently widened results. Mock routing carries ICT date/camera bounds into operational queries, including multi-tool questions.
6. **Empty-report errors and invented health** — division by zero occurred when no cameras existed, and no returned alerts could imply system health. Availability is now unknown/null with zero cameras; recommendations explicitly distinguish no recorded activity from missing ingest. Heartbeat/lease metrics do not prove worker/video health. Camera scope applies to busiest-camera rankings too. Explicit date bounds take precedence over presets; UTC-aware and naive fixture timestamps are handled safely.
7. **Registry failures hidden by successful responses** — ownership/activity/registry failures were logged and ignored; missing registry rows could still lead to checkpoint reads; deletion could claim success after partial failure. These paths now fail with sanitized 503, operational driver-error messages are sanitized before model/checkpoint serialization, missing rows cannot expose/delete orphan checkpoints, and PostgreSQL registry/checkpoint deletion uses the same SQLAlchemy transaction with bound thread identity. MemorySaver deletion clears pending writes as well. Development memory/SQLite and LangGraph chat/activity updates are separate stores/transactions; their limits are described below.
8. **Existing ORM/migration drift** — the expanded original DB suite found that SQLAlchemy unique=True,index=True declared a unique index while unchanged migration 0014 creates a named unique constraint plus an ordinary index. ORM metadata now matches the existing schema. No migration, database column or deployed-schema upgrade was changed.
9. **Invalid existing preview-test fixture** — the combined backend run was delayed by a spinning PreviewWorkerThread. A read-only stack profile located a mocked pipe that returned a truthy MagicMock instead of bytes/EOF. The fixture now blocks until closed and returns EOF, retaining all original assertions and leaving CV code unchanged.
10. **Unrunnable frontend lint** — the existing lint script invoked an undeclared oxlint package. Added pinned development dependency 1.87.0 and updated the lockfile; no UI source/design changes were made.

## Remaining risks and limits

- Existing HMAC Bearer tokens have no expiry/revocation or role-based per-camera permissions. A verified operational account retains the existing shared operational access model. Use a strong random signing secret, protect token distribution and keep the service behind the authorized gateway; key length alone does not prove entropy.
- A trusted proxy secret grants identity assertion and must stay private. Media image/stream consumers must use an authenticated fetch or trusted gateway; a plain img URL cannot attach a Bearer header. These guards intentionally do not publish sensitive media anonymously. The local Agent browser tests validate the existing chat flow, not all protected media consumers in a real proxy environment.
- Explicit anonymous development is not production authentication. Prefer stable signed identities for production.
- Registry activity updates and LangGraph checkpoint writes are not one global transaction. A failed activity update returns 503 even if a checkpoint was already persisted; inspect/reopen history before retrying to avoid duplicate messages. Cross-process concurrent chat/deletion and request idempotency require further integration work. PostgreSQL deletion is transactional; a MemorySaver deletion followed by SQLite commit failure cannot roll back in-memory removal, but returns failure instead of success.
- Live PostgreSQL/Supabase/CUDA, proxy authentication, factual grounding, RAG embedding-model identity and Gemini remain environment verification requirements. Database schemas on the target deployment may differ; do not bypass preflight or auto-reset data.
- Frontend lint warnings remain; deprecation warnings do not change the recorded test pass counts.
