# Email Notification → Alert Center

Validated locally on `dev`, base commit `18ab239`, 2026-10-02. This validation does not deploy to Colab or send real email.

1. **Existing implementation reused.** `Notification` is the durable outbox and delivery history. The persistence worker enqueues face/plate notifications in the Event transaction. `NotificationService` owns cooldown, deduplication, bounded exponential retries and its own background thread. `SMTPEmailAdapter` owns TLS/authentication and optional evidence attachments. Event Center already projects delivery state from the same table. Alerts navigation previously displayed an unavailable-API banner.

2. **Added behavior.** A read-only Alert Center API and page project existing Notification rows, resolve source Event/target/camera labels, and show recipient, delivery status, timestamps and safe failure diagnostics. Failed attempts become FAILED immediately, including while awaiting a bounded retry. Retriable failures retain their cooldown reservation. Recipient rejection/invalid address cannot be treated as successful delivery.

Added: `src/notifications/alerts.py`, `src/notifications/errors.py`, `src/ui/static/alerts.js`, `src/ui/static/alerts.css`, `tests/test_alerts.py`, `tests/test_alerts_browser.cjs`, this document. Backups and validation artifacts are in `scratch/email_alert_center/`. Existing uncommitted Vehicle changes are retained separately.

4. **Migration.** None needed for Alerts. Existing migrations 0008/0010 already provide the outbox fields, Event FKs, uniqueness constraints and indexes. Current local head remains 0011 (the preceding Vehicle color task). No old migration was edited; no production migration was run.

5. **Schema and relationships.** `notifications.id`; exactly one of `event_id → face_events.id` or `plate_event_id → plate_events.id`; optional `target_id` / `vehicle_watchlist_id`; `camera_id`, `channel`, `recipient`, `status`, `created_at`, `sent_at`, `error`, `retry_count`, `next_attempt_at`, existing delivery `payload`. No Alert table or duplicated Event model. The API aliases `recipient` to `recipient_email`, `error` to a safe `error_message`, and returns upper-case delivery statuses while retaining existing lower-case DB values. Existing payload snapshots used to compose email are preserved; the Alert API resolves Event/target relations instead of returning that payload.

6. **Endpoints.** `GET /api/alerts?page=1&page_size=25&status=SENT&event_type=FACE_WATCHLIST_MATCH&camera_id=gate` and `GET /api/alerts/{notification_uuid}`. Status, event type and camera filters are optional. Supported types: FACE_WATCHLIST_MATCH / VEHICLE_WATCHLIST_MATCH; statuses: PENDING / SENT / FAILED / SUPPRESSED. Page size 1–200; stable newest-first order by creation time then ID. List response: `{status, alerts, total, page, page_size}`; detail: `{status, alert}`. Invalid filters return 400, missing ID 404, unavailable DB 503 without provider details. Successful responses use private/no-store caching. `/alerts` serves the existing SPA shell.

7. **Email E2E.** Valid persisted Event → transactional Notification → existing worker → SMTP adapter → commit delivery result. Automated verification uses actual temporary SQLite transactions and a mocked SMTP transport. No SMTP work is added to camera/CV threads and no matching logic is moved into the worker. Missing configuration remains the existing explicit FAILED/CONFIGURED=false outcome; cooldown suppression remains SUPPRESSED.

8. **Alert Center E2E.** Browser fetches API → API reads committed Notification state → UI displays actual recipient and status → detail fetch shows error, retry count, target/plate and source Event link. The source link opens the existing Event Center detail. Loading, empty and HTTP failure states are explicit. Rendering uses textContent, including recipient/camera/error data. The browser verified all four statuses, FAILED filter, source Event detail and Alerts navigation using disposable test fixtures.

9. **Recipient/sender resolution.** Unchanged `EmailConfig.from_env()`: recipients come from comma-separated `DATT_EMAIL_TO`, trimmed and deduplicated. Each configured recipient gets one outbox row. Sender uses `DATT_EMAIL_FROM`, falling back to `DATT_EMAIL_USERNAME`; host/port/TLS/password use existing `DATT_EMAIL_*` configuration. No production address or credential was added to source. Multi-recipient delivery is tested with `.invalid` fixture addresses.

10. **SENT/FAILED.** SENT and `sent_at` are assigned only after the adapter returns successfully, then committed to the DB. SENT means SMTP accepted the message; it does not prove inbox receipt, absence of a later bounce, or reading. On an exception, FAILED and a fixed diagnostic code are committed; `sent_at` stays null. Codes cover timeout, authentication, connection, recipient rejection and generic failure. API also redacts unknown historical error strings. The same failed row can later become SENT after a scheduled successful retry; this is delivery history per Event/recipient, not a separate immutable log of every network attempt.

11. **Deduplication/recovery.** Existing uniqueness constraints on `(event_id, channel, recipient)` and `(plate_event_id, channel, recipient)` prevent duplicate rows. Existing target/camera/recipient cooldown and EventManager dedup remain in place. PostgreSQL target reservation locks and `FOR UPDATE SKIP LOCKED` delivery locks are retained. Retry count now records actual retries already attempted; max_retries still permits one initial attempt plus that many retries. DB errors are caught in the existing worker loop, logged with a fixed safe message, and retried without crashing CV. DB outages cannot themselves be persisted while the DB is unavailable; API returns 503 and the worker recovers. Existing nested enqueue failure isolation preserves the Event, but does not backfill missing Notification rows automatically.

12. **Polling, not realtime push.** No Event/Alert WebSocket or SSE infrastructure was found. Alert Center polls 10 seconds after each completed list request while its screen and browser document are visible, with manual refresh. Requests have a 15-second client timeout. Navigation/filter changes cancel in-flight work; late responses are ignored, with no overlapping list requests. An open detail refreshes with the list. UI explicitly labels polling.

14. **Limits.** Production PostgreSQL/Colab deployment and real SMTP/inbox delivery were not exercised; tests never send real mail. PostgreSQL locking behavior was retained but concurrency was not validated against a live PostgreSQL server here. Existing SMTP delivery is at-least-once: a crash or DB commit failure after provider acceptance can cause a resend; row uniqueness and stable Message-ID cannot guarantee exactly-once email delivery. Alert history retains existing FK deletion behavior, so deleting a source Event can cascade its notifications. Camera/target labels reflect current related records. There is no new acknowledgement/resolution workflow, notification policy for crowd/congestion, or authentication architecture in this task. Preserve the repository's existing deployment access controls. Vehicle OCR/color accuracy readiness is a separate task and is not established by these notification tests.
